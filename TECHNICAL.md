# How Cycles One-Shot works

Notes for developers: how the parts of the Model:Cycles OS that One-Shot touches work, where and how
One-Shot hooks in, and how its sound core is built. Addresses are those of the unpacked MAIN OS
1.13 of the Model:Cycles (base `0x40000400`) unless a section says otherwise. Each was read in the
OS's code; the few that were only observed, not followed through, say so. `machine/os.h` holds
every address the machine uses, with a comment on what was read where.

## 1. The parts

| Path | What it is |
|---|---|
| `src/smp_core.c`, `.h` | the one-shot voice: 6-tap polyphase interpolation at 96 kHz, the fades. Plain C99, no libc, no float, no 64-bit arithmetic |
| `src/smp_coeffs.c` | its table, generated by `tools/gen_coeffs.c` from the design in the Makefile |
| `machine/sampler.c` | the bridge between the Cycles' voice loop and the core (audio side) |
| `machine/pool.c`, `.h` | sample memory: finds, loads and frees samples; the browser and record hooks (UI side) |
| `machine/view.c`, `.h` | the waveform view on the main screen |
| `machine/hooks.S` | the hooks that need assembly |
| `machine/os.h` | every OS address the machine uses; `machine/host_os.h` replaces it in the host tests |
| `machine/build.py` | builds the OS image from your own copy of the official file |
| `uploader/` | a web page that puts audio files on the +Drive over USB (no firmware change needed) |
| `tests/`, `machine/test_sampler.c` | host tests of the core and of the machine with stand-ins for the OS |
| `tools/` | table design, coefficient generator, listening-test renderer |

## 2. Memory

| Range | Use |
|---|---|
| `0x40000400`… | the MAIN OS image (code and constant data), about 1.7 MB |
| `0x409c9c80` + 7094 · n | the kits of the 96 patterns (section 6) |
| `0x42308828` + 0x31c · t | the six voices (section 5) |
| `0x43000000`… | the added machines' payload window (Modded-Cycles' `PAY_ALONE`): One-Shot's code and the moved machine tables from `0x43000000`, variables from `+0x36000` |
| `0x43800000`–`0x46700000` | the sample pool: 47 MB of RAM the Cycles OS leaves unused (the Model:Samples OS keeps its own pool in `0x42800000`–`0x46800000`) |
| `0x80000000`… | SRAM: among others the audio side's copies of the notes' parameters (section 5) and the kit it plays (section 6) |

Up to 0.6 the payload sat at `0x46700000`, the window Modded-Cycles reserves next to Model-TG, and
the pool filled everything below it. Since 0.7 the payload sits where MACRO and ACID put theirs,
so that one combined build can hold several added machines in the same window, and the pool starts
8 MB above it (`POOL` in `machine/build.py`, `POOL_BASE`/`POOL_LIMIT` in `pool.c`).

## 3. Adding a machine

The Cycles OS knows six machines (KICK, SNARE, METAL, PERC, TONE, CHORD). Nothing in it is meant
to grow, but the tables it reads are few and regular. Modded-Cycles found how to add one for its
MACRO machine (`tools/gen_macro.py`, MIT) and later put the steps into one function for any list
of added machines, `gen_macro.added_machine`, which MACRO and ACID use. Since 0.7 `machine/build.py`
calls that registrar from a clone of Modded-Cycles with SAMPLE as the one machine of the list (up to
0.6 it repeated the same steps itself, for one machine):

- **Moved tables.** The table of machine names, the `update` and `render` tables, the table that
  maps a machine to its sound record layout, the parameter descriptors and the knob rows move into
  the payload, one entry longer. Every reference to the old tables is rewritten, and the build
  counts them first.
- **Bounds.** `moveq` instructions that bound machine and descriptor numbers go up by one machine
  (descriptors: 5 more).
- **Detours.** Short stubs teach the MACHINES page, the knob handling and the sound records about
  the new machine.
- **Boot hook.** A sprite mask the OS no longer needs is redirected, and its bytes hold a stub that
  copies the payload's parts from the end of the image to the payload window (`0x43000000`) at start-up; a jump at the
  boot hook leads there.

A parameter descriptor is `0x38` bytes: `+0x00` the machine it belongs to, `+0x08` minimum, `+0x0c`
maximum, `+0x10` default (8.8 values), `+0x2c` long name, `+0x34` short name. The stock table has
76 entries at `0x4010dce0`. SAMPLE adds five, modelled on SNARE's: 76 Start (0–120, default 0), 77
Length (0–120, default 120), 78 and 79 unused, 80 Amp Decay (default 127). SAMPLE is machine 6 and
borrows picture 4 (TONE's) for the MACHINES page; the OS has only six pictures. In a combined build
the registrar assigns the index and the descriptors from SAMPLE's place in the list; the build hands
them to the compiler (`SAMPLE_MACHINE`, `DESC_START`), or, with `CM_SYMBOLS` defined, leaves them as the
undefined symbols `cm_machine_index` and `cm_descriptor_base` that a Level B builder resolves when it places
the compiled object (the object is then compiled once and composed many times; each assembly file has a
section of its own so that such a builder keeps the file order), and the knobs' parameter objects are SNARE's
for every added machine (the accessor detour of notes/18), which is why the Cutoff formatter asks
whether the selected track plays SAMPLE before it writes anything (section 9).

## 4. What One-Shot changes in the OS

Besides the machinery above, seven writes lead into One-Shot's own code. `build.py` checks every
write against the stock bytes before it writes and refuses writes into free space the OS still
points at.

| Address | Stock code | One-Shot |
|---|---|---|
| `0x400a6602` | the browser reads the opened file as a preset (`jsr 0x400a3052`) | `smp_hook_open`: on a SAMPLE track a sample file names the sample in the track's sound instead (section 8) |
| `0x4005afa0` | first 8 bytes of "sound to record", version 2 | `smp_hook_save2`: runs the function, then copies the sample's key into the record |
| `0x4005b054` | the same, version 1 | `smp_hook_save1` |
| `0x4005aecc` | first 8 bytes of "record to sound" | `smp_hook_load`: runs the function, then copies the key back |
| `0x400075f0` | the screen's redraw asks whether to draw (`jsr 0x40076be4`) | `smp_hook_tick`: the loading tick first (section 7) |
| `0x400ffe30` | MainScreenView's vtable entry +16, its draw method `0x4001b22a` | `smp_main_draw` (section 9) |
| `0x4010053c` | the knob view's vtable entry +16, `0x4001e40a` | `smp_knob_draw` |

The three record hooks replace a function's first two instructions (`lea -12(sp),sp`,
`movem.l a2-a4,(sp)`) with a `jmp`; the hook runs those instructions itself, jumps into the body
with a return into its own second half, and calls a C function after the stock work is done
(`machine/hooks.S`). Model-TG and Modded-Cycles' track filter hook the same record functions, so
One-Shot cannot be combined with either; Modded-Cycles' `sample-preview` needs Model-TG and plays
sample files from the same browser. Since 0.7 the build does not list conflicts by hand: it compares
SAMPLE's writes and RAM ranges with every tweak of the clone and declares a conflict where another
tweak writes other bytes to the same address, or runs a payload in SAMPLE's window or pool (every
machine-adding tweak, Model-TG, the track filter), plus `sample-preview` by name; the same whole
write, a sprite mask freed by both, is not a conflict, as in Modded-Cycles' `check_overlaps.py`.
Two optional writes of MACRO are left out: `voice_loop` (a shorter loop with the same values) and
`usb_steady` (an even USB audio clock).

## 5. The audio side

### The voice loop

Every machine supplies two functions, called once per block of 32 frames at 48 kHz (0.67 ms) for
each track that plays it:

```c
void update(int32_t pmod, char *voice, const char *params);   /* then */
void render(int32_t *out, char *voice);                        /* 32 frames, Q31 */
```

- `pmod` is the trig's note in semitones << 16.
- `params` are the note's parameters as 8.8 words: `+0x14` PITCH, `+0x16` COLOR, `+0x18` SHAPE,
  `+0x1a` SWEEP, `+0x1c` CONTOUR, `+0x1e` PUNCH, `+0x22` FINE, `+0x24` DECAY (a byte).
- The note is PITCH − 64 + the trig's note + FINE (±2 semitones), clamped to 0–127; Modded-Cycles'
  notes found the same computation in every stock machine.
- The voice is `0x31c` bytes at `0x42308828 + t · 0x31c`. `+0x34` is set in the block of a trig,
  `+0x38` in the block after it (the OS copies `+0x34` there at the end of a block), `+0x3c` when
  the note ends. Machines set their envelopes up when `+0x38` is set; the sound starts in that
  block. `+0x318` points at a few frames of SRAM for the decimator's state.
- When a track changes machine, `0x400a7ab8` resets its voice: it clears `+0x00`–`+0x3c` (One-Shot
  keeps a marker at `+0x2c` to notice that) and sets the amp envelope's defaults.

### A note's parameters

When a note's sound differs from the track's last one, the audio side copies the sound's 66 bytes
of parameters (k 0–32) to `0x800015ae + 66 · t` (`0x40058a0a`), before any smoothing; One-Shot
reads the sample's key from this copy at the trig. The sound the track played last sits at
`0x800017ec[t]`; setting it to 0 makes the next note copy again. The OS does that itself after a
preview note (`0x4005910e`); One-Shot does it when the browser loads a sample into the sound a
track already plays, because the sound object stays the same.

### The stock chain

TONE and Modded-Cycles' MACRO end their `render` with the stock chain, and so does SAMPLE:

| Address | Function |
|---|---|
| `0x400a9f58` | 2:1 decimator: 64 frames at 96 kHz in, 32 at 48 kHz out. An IIR half-band filter: even frames delayed, odd ones through a 4th-order allpass, added. Flat to 20 kHz (−0.01 dB), about −52 dB from 30 kHz. The Model:Samples OS uses the same code and coefficients |
| `0x400a9252` | amp envelope, once per block |
| `0x400a9430` | VCA: applies the envelope to the 32 frames |
| `0x400a967a` | PUNCH (Modded-Cycles' notes: gain with saturation and a compressor-like envelope) |

The amp envelope keeps its level at `+0x230` (Q31; `0x80000000` is full scale, 0 silence) and
works in three stages (`+0x23c`):

- **Attack.** At the block after a trig the level is set from `+0x248`. The value `0x80000000`
  means full at once; anything else is added each block until the level reaches full. The voice
  reset sets `0x80000000`; KICK does too, PERC sets `0xa2e8ba2f` (full after two blocks), SNARE
  takes a value from a table. TONE and SAMPLE leave the reset's value, so they start at full level.
- **Decay.** Each block multiplies the level by the factor at `+0x250`, which machines take from
  the table at `0x4011d84c` indexed by DECAY. Time to −60 dB:

  | DECAY | 0 | 8 | 16 | 32 | 48 | 64 | 80 | 96 | 112 | 127 |
  |---|---|---|---|---|---|---|---|---|---|---|
  | time | 0.67 ms | 20 ms | 0.1 s | 0.5 s | 1.4 s | 2.8 s | 4.8 s | 7.5 s | 11 s | 15 s |

- **Gate.** With GATE on (`+0x24c`, which the voice loop sets for every machine), the level holds
  until the note ends, then decays.

The VCA ramps linearly within each block from the last block's level (`+0x234`) to the new one.
In the block of a trig it ramps to 0, so a sounding note fades out over 0.67 ms before the new one
starts; with an attack of `0x80000000` the new note's first block skips the ramp and plays at full
level. That is the only click guard the stock chain has; One-Shot's core adds its own at the edges
of a sample (section 10).

### SAMPLE's update and render

`machine/sampler.c`: at the block after a trig, `update` sets the amp chain up the way TONE does,
reads the sample's id from the note's parameter copy, finds the loaded sample (or stays silent if
it is not loaded) and starts the core on the frames Start and Length select. Every block it turns
the note into a ratio, linear within a semitone, and multiplies it by the sample's rate against
48 kHz, so a sample keeps its pitch at any rate, and hands SWEEP and CONTOUR to the filter.
`render` runs the core (64 frames at 96 kHz), the stock decimator, the amp chain and then the
filter (section 16), the last stage of a track as on the Model:Samples. It skips all of that while
no trig is pending and the sample has ended or the envelope is below −102 dB; a filter whose
resonance still rings then runs on silence until it has died away.

## 6. Sounds, kits and records

**A track's live sound.** The project singleton comes from `0x400cf866()`; the track's owner sits
at `+212 + t · 68`, and entry +40 of that owner's vtable returns the sound (the OS's own walk at
`0x40023f0a`; Model-TG and Modded-Cycles use the same).

**A sound** is 100 bytes:

| Offset | Content |
|---|---|
| `+4` | name, 16 bytes |
| `+20 + 2k` | parameter k, 8.8 (k 6 SWEEP at `+32`, k 7 CONTOUR at `+34`, k 11 COLOR at `+42`, k 12 SHAPE at `+44`) |
| `+38` | the machine (high byte of k 9) |
| `+70` | k 25–27: unused by the OS; SAMPLE keeps its key here (below) |

**Kits.** The 96 patterns' kits sit at `0x409c9c80 + 7094 · n`: the six track sounds from `+28`,
then the pool of 64 sounds from `+694` (the sounds that sound locks play). The audio side plays
from a working copy of the current pattern's kit, not from the 96 (`*0x800017e4`, set by its kit
message at `0x40058ddc`); a sound that only that copy holds still has to load.

**Records.** Projects, kits and presets store sounds as records. "Sound to record" exists in two
versions (`0x4005afa0`, `0x4005b054`, arguments record and sound), "record to sound" once
(`0x4005aecc`, arguments sound and record). The load clears k 0–32 of the sound (`0x4005af12`)
and takes record version 2 only. Record slots 24–27 (`+76`) are written as zero and never read.

**SAMPLE's key.** A SAMPLE sound names its sample by three words in k 25–27: the file's inode and
its id. The id is the content hash the file system keeps in the inode (section 7), so it names the
file even after the file moves. The record hooks copy the three words to and from record slots
24–26, so the choice survives saving, loading, copying a sound and putting it into the pool.

**The filter's mark.** Since 0.5 SWEEP is the filter's cutoff, and 0 is a closed lowpass. Sounds
saved by 0.4 and earlier (or by the official OS) have SWEEP at 0, the old "Unused" knob's
default. So the save hook writes 1 into record slot 27 (`+82`), and the load hook sets SWEEP to
64 (open) when a SAMPLE record has no mark. P-locks hold live values and need no such care.

## 7. The +Drive file system

| Address | What |
|---|---|
| `0x40f07cf4` | non-zero once the file system is mounted |
| `0x40fe6df0` | its lock; `+0` the task that holds it. Taken by `0x40001cc4`, given back by `0x40001df6`. The running task is at `0x422fef30` |
| `0x4007de78(ino, out)` | fills `{inode, id, size, inode word 16}`; returns 0 for a file, −1 otherwise. Takes the lock |
| `0x4007baaa(buf, len, handle)` | reads `len` bytes at the handle's position (`{inode, position, -, open}`) and moves it on. Follows the file's chunk map through the cache, so fragmented files read correctly. Takes the lock. Returns the bytes read or −1 |
| `0x401fb8a4` | index of files by id: pairs `{id, inode}` sorted by id, count at `0x401fb8a0`. Built at mount (`0x4007e042`) and again whenever a file is finished |
| `0x4007dc30(id)` | binary search in that index: the pair's number or −1. Call it under the lock |
| `0x4007e3a0` | the OS's own resolver of file references; it looks in the index for a file that left its inode |
| `0x4007c022` → `0x4007e2f6` | closing a file after writing hashes it; the browser and SAMPLE only see files with that hash |

- **The lock lets its holder in again but does not count.** An inner give-back frees it while the
  outer work goes on. The screen's redraw, which runs One-Shot's tick, can itself run from inside
  the file system's work, so the tick leaves the drive alone while the running task holds the lock
  or the drive is not mounted.
- **The id** has bit 0 set; One-Shot uses that to tell a key from an empty one.
- **Sample files** are what the Model:Samples and Elektron Transfer write: a 64-byte header
  (big-endian; `+1` 1 = stereo, interleaved; `+4` bytes of audio; `+8` rate; `+16` the last
  frame's number; `+20` `0x7f` = no loop), the frames as big-endian 16-bit, then 16 zero bytes.
  Presets are 48–160 bytes, which is how the browser hook tells them apart.

**Loading** (`machine/pool.c`). The tick runs from the screen's redraw, about 30 times a second,
in the UI task. It looks at every sound that could play (the 96 kits, the working kit and the six
live sounds), loads what SAMPLE sounds name into the pool (first fit, 128 KB per tick through the
file system's read, stereo mixed to mono as it arrives) and frees what no sound names once no voice
plays from it. A file no longer at its inode is looked up in the index by its id. The redraw also
runs from another task (a screen copy), so the tick takes its own `tas` lock.

## 8. The PRESET browser

- **Opening a file.** At `0x400a6602` the browser calls `0x400a3052` to read the chosen file as a
  preset. On entry `a0` points at the result and `4(sp)` at the handle `{inode, id, size, -}`; the
  browser object (`a2`) holds the target track at `+664`. One-Shot's hook takes the file if the
  track plays SAMPLE and the file is a sample: it hands the OS a copy of the track's sound that
  names the file (the OS then copies the 100 bytes), so everything after it is the stock path.
- **The name.** After any load the browser writes the file's name without its extension into the
  sound (`strlcpy(sound + 4, name, 16)` at `0x400a6650`) and shows "Loaded %s" (`0x400a67a6`).
  SAMPLE sounds get their sample's name this way, for free.
- **Sound locks.** With a step held (`0x4006bdfe`), the browser looks the sound up in the pool
  (`0x40015226`) or takes a free pool slot (`0x40015108`), saves it there through the pool's vtable
  entry +80 (`0x400a680a`) and locks the step to it (`0x400a686a`). The same path works for a SAMPLE
  sound that names a sample, so sample locks need no code of their own.
- **Not One-Shot's doing:** when loading a project asks "Save … before loading?", Yes saves the
  project you leave but does not load the other one. The official OS 1.13 does the same.

## 9. The screen

### Redraw and views

- `0x400075f0` sits in the screen's redraw: `jsr 0x40076be4(view)` asks whether to draw; One-Shot
  runs its loading tick there first.
- The redraw `0x40076c1a(screen, bitmap)` runs when something changed: it clears the bitmap
  (`0x4007133c(bitmap, 0, 1)`), then calls entry +16 of each view's vtable, `draw(view, bitmap)`, no
  return value (call at `0x40076c76`).
- Two views take turns on the main screen. MainScreenView (vtable `0x400ffe20`, draw `0x4001b22a`)
  shows the track while no value is shown. The knob view (vtable `0x4010052c`, draw `0x4001e40a`)
  shows a turned parameter while one is shown. Both draw the whole screen (a lit 64 × 64 box on the
  left, rounded by `0x40070f6e`, the right half dark) and nothing else: no state changes in either
  draw method. Each vtable entry is the only reference to its method.
- UI state: `0x400cf9a8()` returns the UI state object. `0x4006b704(ui)` is non-zero while a value
  is shown (`ui+88` holds the parameter); `0x4006b736(ui)` is non-zero while a trig is held
  (`ui+356`; the held steps are a 64-bit mask at `ui+348`).
- The knob view keeps the shown parameter at `+0x230`, the global descriptor number, which its knob
  handler (`0x4001f4f0`, store at `0x4001f73a`) takes from the knob rows (`0x4001e814`). Its
  timeout counter `+0x238` is counted down in another method (`0x4001efaa`), not in `draw`.
- While a trig is held, the knob view shows the held steps' locked values: per step the lock
  (vtable +96), a sound lock (vtable +108), otherwise the base value (vtable +80).
- The selected track: `0x40012412(0x4000eb90(project))`.
- The current pattern, 0–95: `0x4006a96c(0x400cfd0e())`, which reads the sequencer's current
  pattern (`0x40054828`) and clamps it. MainScreenView reads it so (`0x4001b276`) and writes it as
  `"%c%02d"` with the bank `'A' + p / 16` and the number `p % 16 + 1` (`0x4001b44c`). While another
  pattern is queued (`0x400124e8`), it alternates the two.
- Patterns also have names (the menu's "Ptn Name"): the pattern's object of 732 bytes at the project
  + 5192 + 732 · p, its part at +44, read by `0x4000ce94`: up to 16 characters, "No    Name" when
  empty. SAMPLE's view does not show them.
- A track's level, 0–127, for MainScreenView's level bar (`0x4001b774`): the byte
  `0x40009c5a(project + 116, t)` returns (it clamps t to 0–5 and reads a byte of the object
  returned by entry +52 of that part's vtable, at +10 + 2t), sign-extended. MainScreenView draws
  it from a set of sprites: none at 0, otherwise `1 + (level − 1) · (n − 2) / 126`. It is the only
  caller. MainScreenView is drawn again when the level changes, so a turn of LEVEL moves the bar.

**SAMPLE's view** (`machine/view.c`) takes over the two draw entries. On a SAMPLE track it draws
the main screen itself, and the knob view's screen while Start or Length is turned without a held
trig; everything else goes to the stock method. It reads the sound's live COLOR and SHAPE, so the
markers move while the knob turns.

- **The column**, 21 pixels wide (columns 0–20) and as high as the screen, after the maintainer's
  drawing, lit marks on the dark screen: at the top a lit box (rows 51–63, its corner pixels dark)
  with the current pattern's number in dark; below it an outline (rows 29–48) with TRAK and the
  selected track's number, both lit; at the bottom the level: a frame (columns 6–14, rows 0–26)
  with four ticks on each side (rows 1, 9, 17, 25) and a bar (columns 8–12) that grows from row 2 by
  `1 + (level − 1) · 22 / 126` rows, none at 0, all 23 at 127, as MainScreenView's rule. Its letters
  are the view's own, not the OS's: digits and A–F of 5 × 7 pixels in the shapes of the classic
  character LCD (1 is 3 pixels wide), 1 pixel apart and centred, and TRAK of 3 × 5. Unlike
  MainScreenView it shows only the current pattern, not a queued one.
- **The name's box**, 2 dark columns to the right (columns 23–127, rows 51–63), in the look of the
  browser's title (below): lit, its corner pixels dark, the sound's name in dark letters 2 pixels
  in; a name of 15 characters takes 89 pixels at most of its 101.
- **The waveform**, under the name's box from column 23: 105 columns (`SMP_COLUMNS` in
  `machine/pool.h`) of minimum and maximum that `pool.c` gathers while the file loads.
  NO SAMPLE, LOADING and NOT FOUND stand centred over it.

### Parameter objects and a value's text

The OS keeps an object of 100 bytes for each of its 76 parameters at `0x40a71754 + 100 · i`,
built one by one at boot (`0x400def5c`). The accessor `0x4004df40(i)` returns one; the build's
detour (Modded-Cycles' notes/18) makes SAMPLE's descriptors 76–80 return SNARE's objects 51–55.
A value's text comes from the function at the object's `+0x20`, called as `formatter(object +
0x14, value, buffer)` by `0x4000a70e`; the value is the 8.8 word, the buffer holds 12 bytes at
least, and the screen shows three characters at most. The stock formatters: `0x400456c8` writes
0 … 127 (`sprintf "%d"` of the value >> 8), `0x400456ea` −64 … +63 with a plus sign,
`0x40045bd6` OFF in the middle and ±n. One-Shot puts its own into the shared object of Cutoff
(section 16).

### Bitmaps and drawing

A Bitmap (constructor `0x40070172(this, width, height, pixels, mask)`): `+4` width, `+8` height,
`+12` 32-bit words per column (⌈height / 32⌉), `+16` pixel plane, `+20` mask plane. Pixel (x, y) is
bit `31 − (y mod 32)` of word `x · words + ⌊y / 32⌋`. **y counts from the bottom**, and a set bit is
a lit pixel. Sprites use the same column layout.

| Address | Call | What it does |
|---|---|---|
| `0x400701b8` | `(bmp, x, y, colour)` | one pixel; bit 0 of the colour sets or clears |
| `0x40070dea` | `(bmp, x0, y0, x1, y1, colour)` | fills a rectangle, edges included, clipped. A negative colour inverts (XOR) |
| `0x40070efc` | same | the same, but the four corner pixels stay untouched: a 1-pixel rounding |
| `0x40070f6e` | same | used after filling the main screen's box: short lines near each corner, a larger rounding (only its start was read) |
| `0x4007133c` | `(bmp, colour, mask)` | fills the whole bitmap |
| `0x40071da4` | `(bmp, sprite, x, y, n)` | draws a sprite, a Bitmap with a mask (seen with the machine picture and the browser's arrows; not followed further) |

### Text

`0x40071a04(bmp, font, x, y, flags, format, …)` formats like printf into a 128-byte buffer and draws
the text with x as its left edge and y as the bottom row of its cells. After each character it
leaves one column free: a text is as wide as its characters plus one column per gap (`0x40072152`).

| Flag | Effect |
|---|---|
| `0x01` | fixed width: every cell is the font's widest character + 1, the character centred in it |
| `0x02` | x is the text's centre |
| `0x04` | x is the text's right edge |
| `0x08` | inverted: clears the box (x−1, y−1)–(x+width, y+height), draws, inverts the box |
| `0x10` | clears the box first |
| `0x20` | y is the text's vertical centre |
| `0x40` | y is lowered by the font's height |
| `0x80` | passes the text through `0x4008ef14` first (probably upper case; not checked) |

A font object is 8 bytes, `{0x401117e0, glyphs}` (constructor `0x40072260(obj, glyphs)`, destructor
`0x40072080`). Glyphs: `+0` the widest character, `+4` (u16) how many rows the cells reach below y,
`+6` (u16) cell height, `+8` a byte of width per character code, `+12` per code the u16 number of
its first column (negative: missing), `+16` the columns. A column is a byte for heights up to 8, a
u16 up to 16 and a u32 above, big-endian, its top bit the cell's bottom row.

The OS sets up 14 font objects at boot (`0x400e7ccc`–`0x400e7e1c`):

| Object | Glyphs | Width × height | Below y | Seen in |
|---|---|---|---|---|
| `0x40ea14cc` | `0x40140ab0` | 5 × 9 | 0 | the browser's title; SAMPLE's name. Capitals and digits are 9 rows high, lowercase 7 |
| `0x40ea14d4` | `0x4014120c` | 7 × 9 | 0 | the main screen's "---"; SAMPLE's messages |
| `0x40ea14dc` | `0x40141b08` | 12 × 22 | 0 | large text |
| `0x40ea14e4` | `0x401429ec` | 16 × 22 | 0 | the main screen's "TR%d" |
| `0x40ea14f4` | `0x40145338` | 7 × 15 | 2 | proportional, with descenders |
| `0x40ea14fc` | `0x40143d28` | 6 × 10 | 0 | the knob view |
| `0x40ea14ec`, `0x40ea151c`, `0x40ea1524`, `0x40ea152c`, `0x40ea1534` | | 3–4 × 5–6 | 0–1 | small fonts |
| `0x40ea1504`, `0x40ea150c` | | 3 × 6, 5 × 6 | 0 | entries up to 83 and 45 pixels wide: probably graphics stored as characters |
| `0x40ea1514` | `0x40146180` | 5 × 12 | 2 | not decoded |

**The browser's title bar**, whose look SAMPLE's name box copies: the browser's draw (`0x400a539c`)
clears the screen, draws its title with the small font at (2, 53), flags 0, then calls
`0x40070efc(bmp, 0, 63, 127, 51, −1)`. The result is a lit bar 128 × 13 along the top with its
corner pixels dark and the title in dark letters. SAMPLE's view draws its name box the same way
(text lit, its part of rows 51–63 inverted, its corners dark again); up to 0.8 it drew one bar
across the whole width, and against a digiemu screenshot of the browser all 1664 pixels matched.

## 10. The sound core

The Model:Samples OS plays a sample in two stages, and the core uses the same two:

1. **Interpolation at twice the rate.** For each block of 32 frames at 48 kHz the core computes 64
   frames at 96 kHz. Each frame comes from 6 neighbouring sample frames, weighted by one of 256
   rows of a table; the top 8 bits of the playhead's fraction pick the row.
2. **2:1 decimation** in the stock chain (`0x400a9f58`, section 5).

The playhead is 32.32 fixed point; the ratio is clamped to 1/64 … 8 (−72 … +36 semitones). Before
each block the core copies the frames it will read into a scratch buffer, with silence wherever
they fall outside the start–end window, so the inner loop needs no bounds checks. The voice switches
off once every tap has passed the end. A full-scale frame comes out as `32767 << 15`, half of Q31,
the level the Cycles' machines hand to the decimator.

**Fades.** When the window starts past the sample's first frame, the core fades in over 384 frames
at 96 kHz (4 ms); every window fades out over the 384 frames before the playhead reaches its end.
Both follow the S curve 3x² − 2x³, computed in Q15 integers (at most about 4/32768 off). They count
output frames, so they last 4 ms at any pitch. The frames to the end are worked out once a block,
only near the end. A window that starts at frame 0 keeps its attack, so drum hits lose nothing.
Outside the fades every frame is the plain filter result, bit for bit. The values follow common
practice: Ableton Live fades clip edges by up to 4 ms; FL Studio's sampler fades out over 10 ms by
default and keeps drum attacks in its transient mode.

**Cost.** With gcc 16 at `-O2` the inner loop takes 31 instructions per frame, about 2,200 per track
and block; the decimator adds about 520. A TONE voice takes 5,291 (measured by Modded-Cycles). An
EMAC loop like the Model:Samples' (16 instructions per frame) would halve the core's share.

### The table

One least-squares prototype filter of 1,536 taps (`tools/design.c`), cut into 256 rows of 6 taps.
Each row is centred on the playhead and sums to exactly 32768. The Makefile holds the design:

```
DESIGN := proto 0.34 0.55 100 0   # passband to 16.3 kHz, stopband from 26.4 kHz, weight 100
```

## 11. Start and Length

COLOR (Start) and SHAPE (Length) work as on the Model:Samples. Its descriptors "Sample Start" and
"Sample Length" run from 0 to 120.0 (8.8 values, default length 120.0), and its OS computes the
window at `0x400a62dc` of its MAIN OS: start at Start / 120 of the sample, end at (Start + Length)
/ 120, at most 120. SAMPLE does the same with the full 8.8 values (`SMP_SPAN` in `machine/pool.h`),
so moving Start keeps the length, and 120 splits evenly into slices. The view draws its columns
from the same rule. Sounds saved with 0.2 counted in 128ths of the sample and Length of the rest;
their values now count as above, values past 120 as 120.

## 12. Putting files on the +Drive over USB

Elektron Transfer lists a Model:Cycles' samples but refuses to add any. The Cycles itself answers
the raw file commands that Transfer uses for presets, and the upload page (`uploader/`) uses them
over Web MIDI:

- **Framing.** SysEx `F0 00 20 3C 10 00`, then the message in 7-bit groups (each group of up to 7
  bytes follows a byte with their top bits, the first byte in bit 6), then `F7`.
- **Request:** sequence number (2 bytes), two zero bytes, the type, the body. **Reply:** the
  request's sequence number in bytes 2–3, the type | 0x80 in byte 4, status in byte 5 (1 = done).
- **Commands:** `0x14` read a folder, `0x15` make a folder, `0x43` open a file for writing, `0x45`
  write (8 KB blocks), `0x44` close, `0x24` delete a file, `0x16` delete a folder. A Model:Samples
  answers `0x10`, `0x11`, `0x40`–`0x42`, `0x20` and `0x12` for the same. Paths and names travel as
  Windows-1252.
- Closing hashes the file (section 7), after which the browser lists it and SAMPLE plays it.
- **Deleting.** The OS 1.13 lists `0x16` and `0x24` among the types it takes (the list at
  `0x40112d44`) and builds a message for both (the factory switch at `0x4009247c`); `0x24` parses a
  path like `0x14`. ModdedTransfer deletes files on a Cycles with Model-TG, which hands its `0x20` to
  this `0x24`. Like Elektroid, the page empties a folder before it deletes it, one request at a time,
  and lists the folder again afterwards. It offers no delete for what the Cycles marks protected
  (`factory`), nor for `/incoming`, which the Cycles makes when it formats its drive. ModdedTransfer
  reports that a delete sometimes fails until the Cycles restarts, in Elektron Transfer as well; the
  page then shows the refusal and what is left. SAMPLE needs no change: a slot whose file is gone
  fails at once and stays silent (`test_missing`), a load whose file goes away gives its memory back
  and fails on the next look (`load_step` in `machine/pool.c`), and a loaded sample keeps its memory
  until no sound names it (section 7).

The page writes each audio file as a 48 kHz mono 16-bit sample in the format of section 7 and
checks the size the Cycles reports afterwards. In `/Wavetables`, the folder model27's CHORD Tables
reads (files of k × 256 samples, the first frame on SWEEP 0), it checks each file after the
conversion, before anything is written:
- `tableFrames`: the loader's rule, 1 to 32 frames of 256 samples (the page always writes mono, the
  loader's other rule). A file that fails is not written: its row says why, the status line counts
  it. A WAV at another rate than 48 kHz is resampled by the browser and usually fails here.
- `startsWithSine`, the same test as model27's `tools/wavetable.py`: harmonic 1 of the first 256
  samples in sine phase, DC and every other harmonic under a thousandth of it. A file that fails is
  still written, with a warning on its row and in the status line. The Cycles stays silent while it writes, as with
every file it writes. The protocol facts come from [ModdedTransfer](https://github.com/ktwzk/modded-transfer) (WTFPL), which
follows Elektroid, and from Model-TG's table of the Cycles' file commands (MIT).

## 13. Notes on the Model:Samples OS 1.13

From reading its MAIN OS; addresses here are the Model:Samples'.

- **No machine framework.** The audio block (`0x400586ae`) runs a fixed chain for 7 voices, one for
  preview and the six tracks: voice setup (`0x400a6612`), render (`0x400a6abc`), "Volume + Dist"
  with pan (`0x40055e9c`), a small envelope per track (`0x400a5b28`), the filter per track
  (`0x400a629a`, below), the mixer. Each voice keeps 92 bytes of state from `0x8000cbe4`.
- **The filter** (`0x400a629a(params, buffer, trig bit, track)`, MACSR 0xa0): a highpass stage
  (`0x400a5c1c`, state slot t) and then a lowpass stage (`0x400a5f5a`, slot t + 6), both always.
  One knob: a cutoff word up to 16383 drives the lowpass (the highpass sits at 5 Hz); above, the
  highpass with the word minus 16384 (the lowpass sits at its top, −0.8 dB at 10 kHz, −1.9 dB at
  20 kHz). Each stage is a 2-pole with two states and six coefficients, computed per block from
  tables and glided linearly within the block. The lowpass output is twice a state, shifted
  without saturation (so a loud resonance wraps); the highpass output is a quarter of the input
  minus half that state, so its passband is 12 dB down (made up elsewhere). The descriptors:
  Filter Cutoff k 60, default 0x4000, CC 74, group "Filter"; Filter Reso k 61, default 0, CC 71.
  Its laws, measured by emulating the coefficient path with the OS's own tables, are in
  section 16. One quirk: at cutoff 60 with resonance 32 (words 15360 and 8192; 31744 on the
  highpass side) the index into its 1024-entry log table reaches 2048, so it reads the next
  table and the filter degenerates at exactly that setting.
- **Streaming.** Sample data streams by eDMA from the 64 MB pool into SRAM buffers, about 140
  frames per voice and block; the next voice loads while the current one computes. A trig in one
  block's mask starts the voice in the next, as on the Cycles.
- **Interpolation** at `0x400a7082`: 6 taps, 256 rows, `macw`, 16 instructions per frame. The table
  sits in SRAM at `0x8000a000` in three banks of 1 KB, each holding two taps per row; the reset
  code copies it there from the image at `0x401A44F0`.
- **Decimation** at `0x400a714e` uses the same code and coefficients as the Cycles' `0x400a9f58`.
- **The window**: `0x400a62dc` (section 11), which also handles loop and reverse.
- **Level.** The end of the render (`0x400a7266`) ramps each voice's level linearly within a block,
  as the Cycles' VCA does: normally to full; to 0 in the block of a new trig when a voice flag
  (`+40`) is set; to a quarter each block when another (`+41`) is set and a track value is 0. The
  renderer never resets the level at a note's start, so a note only fades in after such a
  fade-out. When the two flags are set was not followed through.
- **The small envelope** (`0x400a5b28`) rises over 4 blocks (2.7 ms) and falls by 0.37 per block,
  but its level is only read by `0x400a5bba`, which nothing calls.
- **Sample table:** 2,500 slots of 16 bytes from `0x404a2ad0`: data pointer, rate (48000 by
  default), length, rate ratio.

## 16. The filter

**What it is.** The Model:Samples' filter, rebuilt: one knob (SWEEP) that closes a lowpass to the
left of 64 and a highpass to the right, resonance on CONTOUR, 2 poles, 12 dB per octave. Nothing
of Elektron's is in it. Its laws were measured by emulating the Model:Samples' coefficient path
in Python with the tables of your own copy of its OS (the scripts stay out of this repository),
reading the pole positions off the coefficients, and fitting formulas to them:

| Law | Formula |
|---|---|
| Cutoff index i | the 8.8 word on the lowpass side; the word minus 16384 on the highpass side |
| Frequency | fc = 4.918 Hz · 4400^(i / 16384): 5 Hz to 21.6 kHz, about 2 semitones per knob step (within 0.1 % of the Model:Samples over the whole range) |
| Resonance | Q = 0.4918 · 43.8^(R · red / 32512), R the 8.8 word: 0.49 to 21.5, a peak of +3, +10.5, +19 and +27 dB at 32, 64, 96 and 127 |
| Less resonance up top | red = 1 − (fc / 24 kHz)^2.5: a quarter is left at the top |
| Pole radius | r = exp(−π fc / (48000 Q)) |
| Pole angle | θ = 2π fc / 48000 · (1 − 0.70 e^(−R/3300) − 0.233 e^(−R/381)): nearly real poles at R = 0 |
| Lowpass | G / (1 − 2 r cos θ z⁻¹ + r² z⁻²), unity at DC, no zeros |
| Highpass | the input minus that lowpass: 6 dB per octave below the cutoff at low resonance, 12 at high, a +1 dB bump at the cutoff |

**Structure.** The poles are placed with the Chamberlin state-variable form (`src/smp_filter.h`),
whose coefficients f = |1 − r e^(jθ)| and q = (1 − r²) / f realise any pair exactly, real or
complex, and keep low cutoffs precise in Q31. The coefficients (f/2 and q/2, since both reach 2)
come from a 129 × 17 table over cutoff and resonance (`src/smp_filter_tab.c`, 17.5 KB, made by
`tools/gen_filter_table.py` from the laws), bilinear in both; errors from the grid stay under
0.1 % of the frequency and 1 % of Q. Within a block they glide linearly from the last block's
targets, as on the Model:Samples. The loop runs on half the signal and doubles its result: near
the top of the range the bandpass state carries up to twice the output, and only an output
beyond full scale saturates (the Model:Samples wraps there).

One filter runs per track whichever side the knob is on; the side only picks which output is
heard, and the states carry on through a change of side. Two weights, each 0 … 1, shape the
output: y = x + wet (filt − x) with filt = lp + mix (hp − lp). mix is 0 on the lowpass side and
1 on the highpass side; wet is 1 everywhere except within one knob step of the centre, where it
is the distance to the centre over 256, the fine values the OS's smoothing or an LFO passes
through (the same fade as Modded-Cycles' track filter). Both weights glide across the block
like the coefficients, reaching their targets on its last frame. So the knob, a p-lock or an
LFO can cross the centre, or jump from one side to the other within a block, without a step in
the output: a jump from L30 to H30 at full resonance steps no further than the settled filter's
own frames, where 0.5, which cleared the states and started the other side afresh, stepped
six times further (`test_side_jump`). The Model:Samples gets the same effect by running both
stages always, one of them parked; this keeps one stage and the bit-exact off. At exactly 64,
once wet has glided to 0, the filter is off: the block passes untouched, bit for bit, and the
states are forgotten; the next step into a side starts them afresh (a lowpass from the block's
first frame, a highpass from rest) under the glide of wet from 0. A track whose sample has
ended keeps feeding the filter silence until its states drop below 2^-17.

**On the device** the frame loops are `src/smp_filter_cf.S`: 26 instructions per frame for the
settled lowpass and 29 for the settled highpass (wet = 1, mix = 0 or 1, the weights still), and
42 for the blending loop that runs the blocks in which a weight moves or stands between, on the
EMAC in fractional, saturating mode (MACSR 0xa0, which the voice loop already runs in): about
800 instructions per track and block settled, 1,350 while fading, a third to a half of the
core's own cost. `smp_filter_run` picks the loop for the block. The function keeps d2–d7/a2–a6
and MACSR and leaves acc0 and acc1 at zero. `smp_filter.c` holds the same loops as C for the
host, with the EMAC's arithmetic (each product truncated to 2^-39, sums floored to Q31 when
read, saturated), so the host tests predict the device bit for bit; the loops follow each other
instruction by instruction.

**Tests.** `make filter-test` checks the table against the laws, then runs settled sines through
the fixed-point loop at 14 cutoffs × 5 resonances × 7 frequencies and compares with the exact
response of the poles each setting means to place: at most 0.03 dB apart wherever the response
is above −40 dB (within a step of the centre, against the law with its share of the filter). It
also checks that 64 is off bit for bit, the starts, the glide, that the blending loop at wet = 1
and mix = 0 or 1 gives the settled loops' states and output, the jump from side to side against
a reset, the fade within a step of the centre (half the input is left at 128 above it), the fade
out at the centre, a sweep at full resonance, and that a full-scale square at full resonance
saturates and then rings down to nothing. `make machine-test` covers the filter's place in the chain, the ring-out, the reset at
a machine change and the record mark. Against the emulated Model:Samples (the same scripts as
for the laws, with `build/filter_probe` for our side) over 168 settings: median 0.10 dB apart
where its response is above −30 dB, 90 % of the settings within 0.3 dB, the worst 1.3 dB at
20 kHz with the cutoff at the very top and full resonance.

**Cutoff's text.** The knob shows −64 … 63 with 0 in the middle, as the Model:Samples does. The
value window, the TRACK + knob popup and the lock display all get a value's text from the
parameter's object (section 9), so `smp_fmt_cutoff` goes into that object's formatter slot. The
object is SNARE's SWEEP's (SAMPLE's descriptors share SNARE's objects), so the formatter first
asks whether the selected track plays SAMPLE and otherwise writes the stock 0 … 127. The tick
installs it once it finds the stock formatter in the slot; nothing else in the OS changes, and
the parameter itself stays 0 … 127 with 64 in the middle for the LFO, locks, NRPN and saving.

**Differences from the Model:Samples, on purpose.** The highpass passes at unity, not 12 dB down.
On the highpass side the Model:Samples' idle lowpass stage (−0.8 dB at 10 kHz, −1.9 dB at
20 kHz) is not reproduced. A loud resonance saturates instead of wrapping. The log-table quirk
at cutoff 60 / resonance 32 is not reproduced. And the filter sits inside the machine, after
the amp envelope and before Volume + Dist, where the Model:Samples has it after: with DIST above
0 the distortion acts on the filtered signal rather than the filter on the distorted one. The
reason is the Cycles' chain (section 5): a machine renders its block, then the OS's own stages
run for every track, velocity, Volume + Dist and the mixer. A filter behind Volume + Dist would
have to hook that chain for all tracks, the way Modded-Cycles' track filter does at
`0x40059852`; SAMPLE's filter belongs to the machine instead and leaves the chain alone.
